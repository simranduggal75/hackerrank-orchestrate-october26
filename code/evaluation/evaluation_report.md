# Evaluation report

Generated by `python code/main.py evaluate --write-report`. Every number below is computed from the run; nothing is edited by hand. The decision engine is deterministic and uses no language model, so the results are reproducible. The only labelled data are the 32 public samples, which are used for **validation only**. Rules were written from the challenge text and the dataset's structure before any sample was scored, and no rule was loosened to raise a score. Two changes were prompted by reviewing sample mismatches (the system id of a replica copy, and verifying a support message that shows no direct identifier); each is listed in section 6 with a reason from the evidence or the rule logic that stands without the samples.

## 2. Why steps are missed

Only 158 of 193 reference steps (81.9%) name a resource that strict ownership attaches to the subject, so that is the ceiling for step recall without guessing. Missed reference steps by cause:

| Cause | Steps |
|---|---|
| resource not linked to the subject: no link evidence at or before audit_at | 22 |
| resource linked but withheld as unresolved: condition_unestablished | 18 |
| resource not linked to the subject: late_file_link | 7 |
| resource not linked to the subject: convention_candidate | 6 |
| resource linked but withheld as unresolved: unmapped_type | 6 |

Extra predicted steps (not in the reference), by kind: no counterpart in the reference: VERIFICATION/VERIFY_RECORD_ABSENT x 1.

Strict temporal ownership is the default and only mode. A resource is attached to a person only through an exact identifier (email, email hash, phone, user id), an explicit link event, a source-resource reference or an alias recorded at or before `audit_at`. Naming conventions (for example `account_001` for `user_01`), timestamp proximity and activity-log adjacency are never used: measured precision for temporal workflow correlation was about 21% and for activity-id adjacency about 26%, so both were rejected. Consequence: some resources the reference lists cannot be tied to anyone by evidence, and a case that depends on them is reported as `UNRESOLVED` (status `INCOMPLETE`) instead of being guessed. This costs recall; the extra steps listed above are what it costs in precision.

## 3. Internal assessments

`PROVEN_VIOLATION` and `UNRESOLVED` both map to the output status `INCOMPLETE` but are kept distinct: the first means firm evidence shows a state the established rule forbids; the second means the evidence does not allow a verdict. Only `PROVEN_COMPLETE` (every gate G0-G8 passed) yields `COMPLETE`.

Assessments over the 518 evaluation requests (no output file is written by this command): NOT_AUTHORIZED 10, PROVEN_COMPLETE 51, PROVEN_VIOLATION 332, UNRESOLVED 125. Gates failed (a case can fail several): G0 10, G1 353, G2 332, G3 9, G4 2, G5 1, G6 1, G7 114, G8 149.

## 5. Unresolved evidence gaps

These are recorded, never filled by inference. A gap does not create a finding, an ownership link, a resource id or a remediation step.

| Gap code | Evaluation requests affected |
|---|---|
| `condition_unestablished` | 114 |
| `provisional_contradiction` | 1 |
| `provisional_only` | 10 |
| `state_unknown` | 2 |
| `unlinked_fact` | 1 |

* **Record types without an evidence schema.** `UNMAPPED_LOOKUP` (contact/deletion-marker lookups), `CUSTOMER_STATEMENT`, `SECONDARY_IDENTIFIER`, `CACHE_ENTRY`, `PRODUCT_TELEMETRY` and `EMAIL_DELIVERY_LOG` are listed in `policy.UNSUPPORTED`. Cache entries and email delivery logs exist only as ids in the activity log, so their content and state cannot be observed.
* **Rule conditions the evidence cannot establish.** Rule 05 (shared context) needs message text; most support messages carry none. Rule 06 (attachment belongs only to the subject) needs an explicit exclusivity statement; very few attachments have one. Rules 12 and 13 need a supplied retention or hold end date; many retained records have none. Such resources are `UNRESOLVED` (condition unestablished).
* **Screenshots are provisional.** Every OCR-derived fact is provisional: it can neither prove a resource absent nor establish a block, and a later screenshot that contradicts an earlier firm lookup makes the state `UNKNOWN`.
* **Replica system ids.** A surviving replica copy is reported at the resource's home `system_id`, not at a replication system. Evidence for this that does not depend on the samples: in the supplied SQL snapshots every replica-table row that records `origin_system` records the same system as the primary row of the same resource (all resources present in both), and no replica row names a replica, replication or failover system (checked by `tests/test_diagnostics.py`). The account tables carry no such column; there the system comes from the table family (`customer_profiles_*`) and the snapshot header ("Database topology: failover_replica"), which describes a topology of one database. Against this, the activity log does use `account_replication_cluster` (55 rows) and `account_failover_replica` (1 row) as the target of replication-checkpoint events; those are claims about a worker's operation, say nothing about where a record lives, and are not used. The contract does not define `system_id` for replicas, so this is a reasoned reading, not a stated rule.
* **Residual assumption A1.** The footprint is exact-identifier discovery over firm evidence at or before `audit_at`. A violation exposes an identifier, so one outside the footprint would normally leave a hiding-risk signal (gate G8), but a copy that carries no identifier and no link cannot be found.

## 6. Failures found and improvements made

| Failure found | Improvement |
|---|---|
| 13 French requests (`suppression`) were read as non-deletion because the stem `supprim` did not match. | Added the `suppress` stem; 540 of 550 requests now authorize deletion, the other 10 are non-deletion by wording and agree with the intake classification events. |

| Table-dump absence was anchored too loosely. | Absence in a table dump counts only when the subject's own record of the same system and type is in that dump. |
| A search query was copied onto every search hit as if it were an identifier. | The query is an attribute of the hit, not an identifier. |

## 7. Gate G1: why an account is not established

G1 requires an account record that strict ownership ties to the subject and that is proven absent. It is a design choice of this engine, not a stated rule: the contract defines completeness over **every relevant copy** (`problem_statement.md`, "A deletion is complete only when") and does not require a linked `USER_PROFILE` anchor. G1 stands in for "the account copy was examined". A present account always carries identifiers in this dataset (every `FOUND` profile fact in the evidence does), whereas a 404 lookup carries none, so an absent account is exactly the case ownership cannot reach. Failures of G1 by the account evidence that exists (diagnostic only; no decision uses it):

| Cause | Samples | Evaluation requests |
|---|---|---|
| `account_owned_but_not_proven_absent` | 0 | 1 |
| `late_file_link` | 5 | 119 |
| `same_file_empty_collection` | 2 | 30 |
| `same_file_collection_without_subject` | 1 | 113 |
| `same_file_lookup_only` | 4 | 49 |
| `no_account_evidence` | 9 | 41 |

Relaxing G1 would trade false `INCOMPLETE` (current behaviour) for possible false `COMPLETE`; it is not applied.

### Account-anchor alternatives (experimental, not applied)

What the repository says (file:line). `problem_statement.md:24-29`: a deletion is complete only when "every relevant copy has received the treatment required", no sync/import/restore path can recreate the data, retained records hold only permitted identifiers and required records remain. `problem_statement.md:124`: "Determine the resource state at `audit_at` using the available evidence"; workflow statuses and operation results are claims. `problem_statement.md:91,127`: a `COMPLETE` row has verification steps only, each citing a `file_id`, `activity_id` or `audit_id`. `AGENTS.md:298`: "Ignore later evidence". `AGENTS.md:309-310`: the manifest does not say which case a file concerns; "Match evidence through current identifiers, historical identifiers, hashes, resource IDs, system IDs, timestamps, and other grounded links". `AGENTS.md:312`: compare primary and replica tables and the snapshot time. `AGENTS.md:314-316`: a `COMPLETE` verification "must cite the evidence that proves the current compliant state"; never cite evidence captured after `audit_at`. `README.md:59`: SQL captures may hold a primary, regional, reporting or failover replica. Nowhere does the repository require a linked account record, define account absence, or say how a resource is tied to a person other than through the matching evidence listed above.

A waiver also requires at least one owned resource to verify with a citation: without it the answer would be an empty `COMPLETE` with no proof (an empty array is reserved for `NOT_APPLICABLE`, `problem_statement.md:91`). * `baseline`: Production. Requires an account record tied to the subject by strict ownership and proven absent.
* `empty_store`: **Rejected after review (see below).** An account collection reported with 0 rows by an in-time file that also holds the subject's own records. The file is tied to the subject, but nothing documents or corroborates the collection as a complete inventory, and the answer could not contain the account verification step.
* `store_absence`: Adds a non-empty collection (point-in-time snapshot) with no row carrying any of the subject's identifiers, in a file that holds the subject's records. Risk: the snapshots are small slices; absence from a slice proves absence only if the slice includes every row for the subject.
* `closed_world`: Adds files that report only per-resource lookups, or no account evidence at all: no identifier-bearing account record exists for the subject in any in-time evidence. Rests on a schema property (every `FOUND` profile fact carries identifiers) and on the evidence being complete for the subject. Risk: an evidence gap becomes a false `COMPLETE`.
* `record_time`: Contract-excluded reference point: learns ownership from a file captured after `audit_at` (`AGENTS.md:298`, `:316`).

**Steps that cannot be emitted.** A `COMPLETE` answer needs `VERIFY_RECORD_ABSENT` for the account, which needs the account's `resource_id`. Under every contract-supported variant no resource id for the account can be established (the evidence that would give it is the identifier-free lookup or the activity row), so the account step is missing from every flipped answer: `empty_store`: 1 account and 1 other reference step(s) missing across the sample cases it completes; `store_absence`: 1 account and 1 other reference step(s) missing across the sample cases it completes; `closed_world`: 5 account and 5 other reference step(s) missing across the sample cases it completes; `record_time`: 0 account and 2 other reference step(s) missing across the sample cases it completes. Citations improve because a `COMPLETE` row cites its proving files while an unresolved `INCOMPLETE` row cannot.

**Validation, not justification.** In the 22 reference-`INCOMPLETE` samples, 41 of 41 finding resources are ones strict ownership reaches (22 cases have every finding reachable). So in the samples violations are present records that carry identifiers, and the unreachable resources are the absent ones. That agrees with the schema property above, but with 32 cases it cannot show that a hidden violation never occurs.

#### `empty_store` review: rejected

Three requirements were checked. Two fail, so the alternative is not promoted and stays experimental.

1. **Is the empty snapshot documented or independently evidenced as a complete inventory of the store at the audit time? No.** There are 48 account collections in the evidence, 8 of them empty. JSON snapshot entries carry only [('captured_at', 'collection', 'data_store')] plus `records`: no row count, scope or completeness field. 9 stores report different record counts at different times inside a single bundle, so a bundle is a time series of slices. The SQL inventories do document scope, but only as the *systems* captured and a capture time (`snapshot_scope(origin_system, captured_at)`); the largest account collection holds 4 rows while there are 850 identities, so no collection is a platform-wide inventory. Independent corroboration is also missing: of 212 subject/file pairs, 0 have any other account observation within 48 hours that could confirm or contradict the collection, so completeness can be neither shown nor falsified from the evidence.
2. **Is the snapshot tied to the subject with evidence available at or before `audit_at`? Yes, but only to the file.** The subject is linked to the file by exact identifiers in records of other types (retained audit records, tombstone references), all captured at or before `audit_at`; no case-number pattern or sample answer is used. That shows the file mentions the subject, not that its account collection covers the subject.
3. **Does the output contract permit `COMPLETE` when the account step cannot be emitted? Formally yes, in substance no.** The contract does not name a mandatory step, but `COMPLETE` must be "verification steps proving the current state" (`problem_statement.md:91`), each citing evidence that proves the compliant state (`AGENTS.md:314`), and completeness is defined over every relevant copy (`problem_statement.md:26`). The empty collection gives no `resource_id`, so no `VERIFY_RECORD_ABSENT` for the account exists. Of the 10 cases this variant would complete, 0 contain an account step, and their steps are only {'VERIFY_DATA_FLOW_DISABLED': 1, 'VERIFY_RECORD_PRESENT': 10, 'VERIFY_RECORD_REDACTED': 2, 'VERIFY_RESTORE_BLOCKED': 1}: none verifies that anything was deleted, so the answer would assert completion without stating the fact that makes it complete.

What remains true: the empty collection is consistent with an absent account, and every flipped case has the snapshot captured at the audit time. That is a reason to keep looking for corroboration, not a proof.

## 8. Known limitations

* Recall on the samples is bounded by ownership (section 2); the engine prefers an `UNRESOLVED` `INCOMPLETE` to a guessed answer. Cases the reference marks `COMPLETE` but strict evidence cannot prove are reported `INCOMPLETE`, as the confusion matrix shows.
* Unresolved cases still receive verification steps for the compliant resources that are proven, but no finding or remediation is invented for resources the evidence does not establish.
* Screenshots are read with the Windows OCR engine (Windows.Media.Ocr through PowerShell) and are provisional evidence. Measured with the engine disabled: no status and no step changes in any of the 550 requests; only gate diagnostics change in 5 cases, which are `INCOMPLETE` either way. The submission therefore does not depend on OCR being available (`tests/test_ocr_independence.py`).
* The sample set is small (32 cases); its numbers are indicative, not a confidence interval.
* Rows are sorted by `case_id` as plain strings (`case_100` before `case_33`), the literal reading of "sorted by case_id"; the ids are not zero-padded.
* `evaluation/usage_report.md` records that the final run makes no model call; it does not cover the coding agent that built the system.
